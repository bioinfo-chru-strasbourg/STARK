Application Configuration

This document describes the configuration variables for the STARK application, as defined in config/default.app.

Example of application configuration file:

#!/bin/bash
## STARK application EXOME

# DEFAULT ENV
######################
source_app $CONFIG_DEFAULT_APP

# APPLICATION INFOS
#####################
APP_NAME="EXOME"
APP_RELEASE="1.0"
APP_DESCRIPTION="Application to detect germline mutations in exome sequencing data"
APP_GROUP="GENETIC"
APP_PROJECT="EXOME"

# PIPELINES PARAMETERS
#######################

# PIPELINES
PIPELINES="bwamem.gatkHC.howard bwamem.gatkUG.howard"

# INTERVAL_PADDING
INTERVAL_PADDING=100

Application Infos

Application information that describes the application, including its name, release, description, group, and project.

Source application configuration

Specify the base application configuration to inherit from, if any. Use "source_app <APPLICATION_NAME_OR_FILE>" to include another application's configuration. Include the default configuration "$CONFIG_DEFAULT_APP" for an application that do not heritate from another. To configure an application that inherates from another, specify the application with its name or file. To configure with a plugApp application (that modify some variables of the base application configuration, without fully inheriting it), add the corresponding plusApp in the source_app line.

  • Example
    • source_app $CONFIG_DEFAULT_APP (default application configuration)
    • source_app $CONFIG_DEFAULT_APP,SOMATIC_PARAMETERS (e.g. a "SOMATIC" application with "SOMATIC_PARAMETERS" plugApp)
    • source_app SOMATIC (e.g. a "SOLIDTUMOR" application inheriting from the "SOMATIC" application)

APP_NAME

Name of the application. Auto-detect by file name using pattern: <APP_NAME>.app. This name is used to identify which application to apply, with parameter --app|--application (e.g. --application=EXOME or --application=EXOME.app). Also usefull to include specific rules if exists (e.g. $RULES_APP/$APP_NAME.rules.mk/*rules.mk, <APP_NAME>.rules.mk/*rules.mk).

  • Default: "DEFAULT"

APP_RELEASE

Release of the application. Should follow Semantic Versioning system (i.e. MAJOR.MINOR.PATCH)

  • Default: "1.0.0"

APP_DESCRIPTION

Description of the application. Will be using parameter --applications_infos in the command line to display it in the help message of the application.

  • Default: "No description available for this application"

APP_GROUP

Group associated with the application. Use to structure data in the repository folder (i.e. <GROUP>/<PROJECT>). Leave it blank for no group (i.e. UNKNOWN).

  • Default: "UNKNOWN"

APP_PROJECT

Project associated with the application. Use to structure data in the repository folder (i.e. <GROUP>/<PROJECT>). Leave it blank for no project (i.e. UNKNOWN).

  • Default: "UNKNOWN"

Pipeline parameters

Pipelines parameters define the configuration for the analysis pipelines, including the choice of aligners, callers, and annotators, and also intermediate steps (such as the post-alignment and post-calling steps). Moreover, specific rules should be defined for each component to ensure proper execution of the pipelines.

ASSEMBLY

Assembly to use for the analysis, in UCSC format, such as hg19 or hg38. Assembly is automatically detected in manifest file (configured in the SampleSheet of each run), if any.

  • Default: "hg19"

  • Examples:

    • "hg19"
    • "hg38"

PIPELINES

Pipelines to use for the analysis. A pipeline is defining with an aligner, a caller and an annotator. Each pipeline should be defined with a valid combination of aligner, caller, and annotator, in format ALIGNER.CALLER.ANNOTATOR. All corresponding rules should be defined in the rules files. If no pipeline is finally defined, the default pipeline will be applied.

  • Default: "bwamem.gatkHC.howard"

  • Format: "ALIGNER1.CALLER1.ANNOTATOR ALIGNER1.CALLER2.ANNOTATOR1 ALIGNER2.CALLER1.ANNOTATOR1"

  • Examples:

    • "bwamem.gatkHC.howard" (BWA mem alignment, GATK HaplotypeCaller, HOWARD annotator)
    • "bwamem.VarScan.howard" (BWA mem alignment, VarScan variant caller, HOWARD annotator)
    • "bwamem.gatkHC.howard bwamem.gatkUG.howard bwamem.VarScan.howard" (Multiple pipelines with different callers, all using BWA mem alignment and HOWARD annotator)

  • Notes:

    • If variables ALIGNERS, CALLERS, and ANNOTATORS are defined, this variable will be automatically generated by adding a combinations of all aligners, callers and annotators.

ALIGNERS

Aligners to use for the analysis (see PIPELINES parameter). A corresponding rules file should exist for each aligner.

  • Default: ""

  • Examples (available aligners):

    • "bwamem" (BWA mem alignment algorithm)
    • "bowtie" (Bowtie2 alignment algorithm)
    • "star" (STAR alignment algorithm for RNA-Seq data)

CALLERS

Callers to use for the analysis (see PIPELINES parameter). A corresponding rules file should exist for each caller.

  • Default: ""

  • Examples (available callers):

    • "gatkHC" (GATK HaplotypeCaller)
    • "gatkUG" (GATK UnifiedGenotyper)
    • "VarScan" (VarScan variant caller)
    • "MuTect2" (GATK MuTect2)

ANNOTATORS

Annotator to use for the analysis (see PIPELINES parameter). A corresponding rules file should exist for each annotator.

  • Default: ""

  • Examples (available annotators):

    • "howard" (HOWARD annotator)
    • "snpeff" (SnpEff annotator)

POST_SEQUENCING_STEPS

Post-sequencing steps are the steps to be executed after FASTQ processing and before alignment. The steps are defined as makefiles rules. Check available steps by using the command STARK --pipelines_infos.

  • Format: "step1 step2 step3"

  • Default: "" (nothing to do)

  • Available steps (not up-to-date):

  • Examples:

    • "" (nothing to do)

POST_ALIGNMENT_STEPS

Post-alignment steps are the steps to be executed after alignment and before calling. This sequence correspond to a BAM file processing just after the alignment. The steps are defined as makefiles rules. Check available steps by using the command STARK --pipelines_infos. Usage example: steps "sorting realignment clipping compress" will process the $ALIGNER.compress.clipping.realigned.sorting.bam BAM file to generate the final $ALIGNER.bam BAM file after all specified post-alignment steps. Thus, this BAM file will be 1/ sorted, 2/ realigned, 3/ clipped and 4/ compressed.

  • Format: "step1 step2 step3"

  • Default: "sorting markduplicates realignment recalibration compress"

  • Available steps (not up-to-date):

    • sorting: BAM sorting
    • compress: BAM compression (see $BAM_COMPRESSION variable)
    • realignment: local realignment
    • recalibration: reads recalibration
    • gencore: gencore is a tool for fast and powerful deduplication for paired-end next-generation sequencing
    • markduplicates: Mark duplicated reads in BAM with PICARD MarkDuplicates. Use BARCODE_TAG to specify tag
    • clipping: BAM Clipping according to primer definition in manifest file, if any

  • Examples:

    • "sorting realignment clipping compress" (for Amplicon technology)
    • "sorting markduplicates realignment compress" (for Capture technology)
    • "sorting gencore markduplicates realignment compress" (for UMI technology)

POST_CALLING_STEPS

Post-calling steps are the steps to be executed after variant calling and before annotation. This sequence correspond to the VCF file generated just after the calling. The steps are defined as makefiles rules. Check available steps by using the command STARK --pipelines_infos. Usage example: steps "recalibration filtration" will process the $ALIGNER.$CALLER.filtration.recalibration.vcf VCF file to generate the final $ALIGNER.$CALLER.vcf VCF file after all specified post-calling steps. Thus, this VCF file will be 1/ recalibrated and 2/ filtered.

  • Format: "step1 step2 step3"

  • Default: "normalization"

  • Available steps (not up-to-date):

    • sorting: VCF sort
    • normalization: VCF normalization for post calling by splitting variants into one line (using BCFTools)
    • variantnormalization: VCF normalization splitting variant in 1 line, removing duplicates, fixing GT ploidy and recalculate tags (using BCFTools)
    • variantrecalibration: VCF recalibration (using GATK4). Include variantfiltration if no recalibration possible
    • variantfiltration: VCF filtration (using GATK4)

  • Examples:

    • " " (to avoid at this pipeline step, see POST_CALLING_MERGING_STEPS)
    • "normalization" (to minimal normalize the VCF file after calling)
    • "variantnormalization" (to prevent multiallelic or multiploidy inconsistency, recalculate tags)
    • "variantnormalization normalization variantfiltration" (for gene panel)
    • "variantnormalization normalization variantrecalibration variantfiltration" (for exome or genome)

  • Warning:

    • Using variantnormalization recalculate tags (with BCFTools), including VAF tag, which can not be properly recalculated with HOWARD VAF normalization.

  • Format: "step1 step2 step3"

  • Default: " "

  • Available steps (not up-to-date):

    • normalization: VCF normalization for post calling by splitting variants into one line (using BCFTools)
    • variantnormalization: VCF normalization splitting variant in 1 line, removing duplicates, fixing GT ploidy and recalculate tags (using BCFTools)
    • variantrecalibration: VCF recalibration (using GATK4). Include variantfiltration if no recalibration possible
    • variantfiltration: VCF filtration (using GATK4)

  • Examples:

    • " " (to avoid at this pipeline step, see POST_CALLING_MERGING_STEPS)
    • "normalization" (to minimal normalize the VCF file after calling)
    • "variantnormalization" (to prevent multiallelic or multiploidy inconsistency, recalculate tags)
    • "variantnormalization normalization variantfiltration" (for gene panel)
    • "variantnormalization normalization variantrecalibration variantfiltration" (for exome or genome)

RULES_APP

Add specific rules to load (see PIPELINES parameter). These files will be added to the list of rules files from APPS folder. Variable $APP_FOLDER corresponds to the folder of the current app. For inheritance, use RULES_APP="$RULES_APP MYGROUP/*.rules.mk".

  • Default: ""

  • Examples:

    • "MYGROUP/*.rules.mk"
    • "$APP_FOLDER/*.rules.mk"

Demultiplexing

BARCODE_MISMATCHES

Number of allowed barcode mismatches during demultiplexing. This value specifies how many mismatches are allowed when matching barcodes during the demultiplexing process.

  • Default: 1

STARK_DEMULTIPLEXING_BASES_MASK

Bases mask for demultiplexing. This setting determines how the sequencer reads are interpreted during the demultiplexing process.

  • Default: "" (auto from SampleSheet)

  • Examples:

    • "" (auto from SampleSheet)
    • "Y150,I10,Y10,Y150"
    • "Y150,I8,Y10,Y150" (UMI index2)

STARK_DEMULTIPLEXING_MASK_SHORT_ADAPTATER_READ

Short adapter read mask for demultiplexing. This setting determines the mask for short adapter reads during the demultiplexing process. If demultiplexing UMI within a read must be set to 0 for Agilent XTHS kits.

  • Default: "" (auto)

  • Examples:

    • "" (auto)
    • "Y10" (short adapter read of 10 bases)

STARK_DEMULTIPLEXING_READS_MAPPING

Read mapping for demultiplexing. This setting defines the order of reads in the FASTQ files for demultiplexing. Redefine FASTQ files in order to identify R1, R2, I1 and I2.

  • Default: "" (corresponding to "R1 I1 I2 R2")

  • Examples

    • "" (default, corresponding to "R1 I1 I2 R2")
    • "R1 I1 R2 R3" (UMI index2)

ADAPTER_STRINGENCY

Adapter stringency for demultiplexing. For BCL2FASTQ demultiplexing (see doc).

  • Default: 0.9

STARK_DEMULTIPLEXING_BCL2FASTQ_OPTIONS

BCL2FASTQ demultiplexing options (see doc). This setting allows you to specify additional options for the BCL2FASTQ demultiplexing command.

  • Default: "--no-lane-splitting --create-fastq-for-index-reads"

  • Examples:

    • "--no-lane-splitting --create-fastq-for-index-reads" (default)
    • "--no-lane-splitting" (without creating fastq for index reads)

FASTQ_DEMULTIPLEXING_COMPRESSION_LEVEL

FASTQ compression level for demultiplexing FASTQ files. This specifies the zlib compression level (1-9) used for FASTQ files during demultiplexing (BCL2FASTQ). If FASTQ_DEMULTIPLEXING_KEEP=1, we suggest a high level of compression (at least 5).

  • Default: 1

FASTQ_DEMULTIPLEXING_KEEP

Keep demultiplexing FASTQ files (1/TRUE/YES/Y or 0/FALSE/NO/N). This setting determines whether the demultiplexed FASTQ files are kept into results after processing.

  • Default: 0

SEQUENCING_DEMULTIPLEXING_FOLDER

Folder for storing demultiplexed FASTQ files within the sequencing results ($SAMPLE.sequencing folder).

  • Default: "demultiplexing"

FASTQ Processing

FASTQ_COMPRESSION_LEVEL

Compression level for main FASTQ files (1-9). Used by FASTP with zlib compression.

  • Default: 1

ENABLE_ADAPTER_TRIMMING

Enable or disable adapter trimming for FASTQ files. If enabled, FASTP will trim adapters from the reads based on the detected adapter sequences (autodetect). This setting only affects adapter trimming and does not impact other FASTQ processing steps.

  • Note: Adapter trimming may affect read length and quality statistics.

  • Options: 0 (disabled) or 1 (enabled)

  • Default: 0 (disabled)

FASTQ_QUALITY_FILTERING

Enable or disable read quality filtering for FASTQ files. If enabled, reads with quality below the specified threshold will be removed.

  • Default: 0 (disable)

POLY_G_MIN_LEN

Enable or disable polyG tail trimming for FASTQ files. If enabled, FASTP will trim polyG tails from the reads. By default, trimming is automatically enabled for Illumina NextSeq/NovaSeq data. The minimum length to detect polyG in the read tail.

  • Default: 0 (disabled)

READ_LENGTH_REQUIRED

Enable or disable read length filtering for FASTQ files. If enabled, reads shorter than the specified length will be discarded.

  • Default: 0 (disabled)

UMI_LOC

UMI extraction location for FASTQ files. If not specified, UMI extraction will be disabled. If UMI extraction is enabled, specify the location of the UMI within the reads or indexes. See FASTP/UMI TOOLS documentation for more information.

  • Available locations:

    • "index1": the first index is used as UMI. If the data is PE, this UMI will be used for both read1/read2.
    • "index2": the second index is used as UMI. PE data only, this UMI will be used for both read1/read2.
    • "read1": the head of read1 is used as UMI. If the data is PE, this UMI will be used for both read1/read2.
    • "read2": the head of read2 is used as UMI. PE data only, this UMI will be used for both read1/read2.
    • "per_index": read1 will use UMI extracted from index1, read2 will use UMI extracted from index2.
    • "per_read": read1 will use UMI extracted from the head of read1, read2 will use UMI extracted from the head of read2.

  • Default: "" (disabled)

UMI_BARCODE_PATTERN

Pattern for UMI and optional cell barcodes within the reads or indexes. If not specified, UMI extraction will be disabled. Otherwise, UMI extraction will be performed according to the specified location. Pattern will be used to extract UMIs and optional cell barcodes from the reads or indexes.

If UMI_LOC is "per_index" or "per_read", and UMI_BARCODE_PATTERN is defined as "NNNNN", it with be redefined as "NNNNN-NNNNN". Only length of the first part of the duplex barcode will be used with FASTP. See FASTP/UMI TOOLS documentation for more information.

  • Default: "" (disable)

  • Examples:

    • "NNNNNNNNNN" (for simplex)
    • "NNNNN-NNNNN" (for duplex)

FASTP_ADDITIONAL_OPTIONS

Additional options to pass to FASTP. This allows you to pass any additional command-line options to FASTP. See FASTP documentation for available options.

  • Default: "" (no additional options)

  • Examples:

    • "--trim_front1 3 --trim_front2 3"

FASTQ_PROCESSING_STEPS

All steps to process input FASTQ files, after sequencing and demultiplexing (if any).

  • Format: `"step1 step2 step3"

  • Available steps:

    • fastq_reheader: FASTQ reheader to integrate index within FASTQ comment Illumina tag (e.g. 1:N:0:xxx). Nothing done if already integrated.
    • fastq_clean_header: FASTQ read head formatting, especially SAMTOOLS tags. Nothing done if not needed.
    • compress: FASTQ files compression (see FASTQ_COMPRESSION_LEVEL).
    • sort: Sort FASTQ using read name.
    • fastp: Process FASTP algorithm and report, UMI extraction, quality filtration...
    • umi_tools: Process UMITools algorithm for UMI extraction.

  • Default: "fastq_reheader sort fastp fastq_clean_header compress"

  • Examples:

    • "fastq_reheader sort fastp fastq_clean_header compress" (for default sorting and compression)
    • "fastq_reheader sort umi_tools fastp fastq_clean_header compress" (for UMI technology using umi tools)
    • "sort compress" (for only sorting and compression)
    • "" (for no processing steps, FASTQ files will remain unprocessed and identical as from demultiplexing)

Archives

CRAM_OPTIONS

Final CRAM options for compression (archive.cram). Specify the CRAM compression options to use when creating the archive.cram file.

  • Default: "version=3.0,level=9,no_ref"

  • Examples:

    • "version=3.0,level=9,no_ref" (default compression)
    • "version=3.0,level=6" (for faster compression with lower level and no reference included)
    • "version=3.0,level=9,no_ref,use_lzma,use_bzip2,use_fqz,seqs_per_slice=100000" (for maximum compression with additional algorithms)

CRAM_REMOVE_TAGS

Final CRAM options for tags (archive.cram). Remove tags from the CRAM file during compression. Specify the tags to be removed as a comma-separated list.

  • Default: "BD,BI" (remove BD and BI tags by default)

  • Examples:

    • "BD,BI,OQ" (remove BD, BI, and OQ tags)
    • "" (do not remove any tags)

Alignment and post alignment

BARCODE_TAG

Specify the barcode tag to use for marking duplicates in BAM files. Barcode to use for Mark Duplicates. If not null, Mark Duplicates will consider this tag. See PICARD documentation for more information.

  • Default: ""

  • Examples:

    • "BC" (default Illumina, 10X genomics)
    • "RX" (standard SAM UMI barcode tag)
    • "BX" (UMI)

PICARD_MARKDUP_OPTICAL_DEDUP

Regular expression that can be used to parse read names in the incoming SAM file. Set variable to "READ_NAME_REGEX=null" to disable optical deduplication.

  • Default: ""

  • Examples:

    • "-READ_NAME_REGEX null" (disable optical deduplication)

BAM_COMPRESSION

Final BAM compression level (for <ALIGNER>.bam).

  • Default: 9

BAM_VALIDATION_COMPRESSION

Validation BAM compression level (<ALIGNER>.validation.bam).

  • Default: 5

GENCORE_SUP_READS

Gencore supporting reads threshold. The minimum number of supporting reads required to form a cluster. This parameter helps to control the stringency of clustering in Gencore. This setting is particularly useful when dealing with low-frequency variants or noisy data. Higher values increase stringency, lower values make clustering more permissive.

  • Default: "" (corresponding to "--supporting_reads 1", see gencore doc)

  • Examples:

    • 2 (keep clusters with 2 or more supporting reads, ultrasensible filter)
    • 1 (replace Picard Markduplicates dedup)

GENCORE_SCORE_THREESHOLD

Gencore score threshold for forming consensus reads. Higher values increase stringency, lower values make clustering more permissive.

  • Default: "" (corresponding to "--score_threshold 6", see gencore doc)

  • Examples:

    • 8 (recommended for dup-rate < 50% to keep all DNA fragments and discard low quality unoverlapped mutations)
    • 6 (default, see gencore doc)

  • Default: "" (corresponds to --score_threshold 6)

GENCORE_RATIO_THREESHOLD

Gencore ratio threshold for major base comparison. If the ratio of the major base in a cluster is less than this threshold, it will be further compared to the reference. The value should be 0.5~1.0, and the default value is 0.8.

  • Default: "" (corresponding to "--ratio_threshold 0.8", see gencore doc)

  • Examples:

    • 0.8 (default, see gencore doc)
    • 0.9 (more stringent, require higher major base ratio)

GENCORE_DIFF_THREESHOLD

Gencore UMI difference threshold for merging reads. If two reads with identical mapping position have UMI difference <= <umi_diff_threshold>, then they will be merged to generate a consensus read.

  • Default: "" (corresponding to "--umi_diff_threshold 2", see gencore doc)

  • Examples:

    • 2 (default, see gencore doc)
    • 1 (more stringent, require lower UMI difference)

GENCORE_QUAL_THREESHOLD

Gencore quality threshold for base comparison. This sets the minimum quality score for considering a base in the consensus read. Higher values increase stringency, lower values make clustering more permissive.

  • Available options:

    • "--high_qual <value>" (the threshold for a quality score to be considered as high quality. Default 30 means Q30. (int [=30]))
    • "--moderate_qual <value>" (the threshold for a quality score to be considered as moderate quality. Default 20 means Q20. (int [=20]))
    • "--low_qual <value>" (the threshold for a quality score to be considered as low quality. Default 15 means Q15. (int [=15]))

  • Default: "" (corresponding to default quality, see gencore doc)

  • Examples:

    • "--moderate_qual 20" (Moderate defined as Q20)
    • "--high_qual 20 --moderate_qual 15 --low_qual 10" (Threasholds changed to Q20, Q15, Q10)

GENCORE_COVERAGE_SAMPLING

Gencore coverage sampling for genome scale coverage statistics (value 10000 means 1/10000). This option sets the sampling rate for genome scale coverage statistics in Gencore. The higher the value, the lower the sampling rate, which can improve performance at the cost of accuracy.

  • Default: "" (corresponding to "--coverage_sampling=10000", see gencore doc)

  • Examples:

    • 10000 (default, see gencore doc)
    • 5000 (higher sampling rate, more accurate but slower)

Calling and post calling

USE_VCFDBSNP_WITH_GATK

Enable VCF DBSNP for GATK calling and annotation. This option allows GATK to use the VCF DBSNP if the file is available and not empty. dbSNP database as VCF is used to annotate variant ID in ID VCF field and to provide known variants for GATK calling and annotation (if any) See https://gatk.broadinstitute.org/hc/en-us/articles/360046786692-VariantAnnotator#--dbsnp. This option allow GATK to use the VCF DBSNP for calling and annotation, if the file is available and not empty. If not, GATK will be used without DBSNP for calling and annotation. See rules that use GATK for calling and annotation (e.g. gatkHC, gatkUG, MuTect2) for more information about the use of VCF DBSNP for GATK calling and annotation. Variable VCFDBSNP_WITH_GATK is generated automatically and indicates whether to use the VCF DBSNP file for GATK calling and annotation. See VCFDBSNP variable for the VCF DBSNP file path (in databases.app).

  • Default: 0 (do not use VCF DBSNP with GATK)

  • Examples:

    • 1 (enable use of VCF DBSNP with GATK)
    • 0 (do not enable use of VCF DBSNP with GATK)

VCFDBSNP

VCF DBSNP path for GATK calling and annotation. Path to the dbSNP database as VCF used for GATK calling and annotation (if any). This file need to be available and not empty for GATK to use it for calling and annotation (if USE_VCFDBSNP_WITH_GATK=1). This variable is automatically defined in default configuration in databases.app.

  • Default: "" (corresponding to default VCF DBSNP defined in databases.app, depending on ASSEMBLY)

  • Examples:

    • "" (use default VCF DBSNP defined in databases.app)
    • "$FOLDER_DATABASES/dbsnp_138.hg19.vcf.gz" (use specific VCF DBSNP file for GATK calling and annotation)

IGV session xml file (*igv_session.xml) is generated with Samples and Runs files (BAM, VCF, BED). Parameters select files through patterns and folder depth. Be aware that these patterns should match the files available in the repository for the samples or runs.

IGV_SESSION_PATTERNS_SAMPLE_DEFAULT

IGV session XML file (*igv_session.xml) patterns for samples. These patterns define which files will be included in the IGV session for samples. Be aware that these patterns should match the files available in the repository for the samples. Theses files can be VCF, BAM, CRAM, or BED files related to the sample.

  • Default: ' $SAMPLE.final.vcf.gz $SAMPLE*Design*bed $SAMPLE*Panel*bed *Design*vcf.gz *Panel*vcf.gz *bam *cram '

  • Examples:

    • ' $SAMPLE.final.vcf.gz $SAMPLE*Design*bed $SAMPLE*Panel*bed *Design*vcf.gz *Panel*vcf.gz *bam *cram ' (default)
    • ' $SAMPLE.final.vcf.gz $SAMPLE.*.bam $SAMPLE.*.bam.bai ' (alternative pattern for samples, only main VCF file and BAM files without additional files for Panel or Design)

IGV_SESSION_PATTERNS_RUN_DEFAULT

  • Default: ' *.final.vcf.gz *Design*bed *Panel*bed *Design*vcf.gz *Panel*vcf.gz *bam *cram '

  • Examples:

    • ' *.final.vcf.gz *.bam *.bam.bai ' (alternative pattern for runs, only main VCF file and BAM files without additional files for Panel or Design)

Folders

Folders used for the analysis. These folders will be automatically created if not exist. The main folder is defined by STARK_FOLDER_MAIN variable, and all other folders are defined as subfolders of this main folder. Folders can be redefined as absolute path, but we suggest to keep them as subfolders of the main folder for better organization and management of the data. Folders like tools and databases contains tools and databases needed for the analysis, and will be used by the rules of the analysis. Folders like input and output are used to store input data and results of the analysis, and will be used by the rules of the analysis.

STARK_FOLDER_MAIN

This is the main folder for the analysis, and all other folders are defined as subfolders of this main folder. This folder will be automatically created if not exist, either during setup (for folders tools and databases) or during the analysis to store all the data and results of the analysis.

  • Default: "/STARK"

FOLDER_TOOLS

All tools needed for STARK, and more, including STARK. This folder will be automatically created during setup if not exist, and will be used to store all the tools needed for the analysis, including STARK itself. This folder will be used by the rules of the analysis to access the tools needed for the analysis.

  • Default: "$STARK_FOLDER_MAIN/tools"

FOLDER_DATABASES

All databases needed for STARK, and more. This folder will be automatically created during setup if not exist, and will be used to store all the databases needed for the analysis, including reference genomes and mandatory databases for calling and annotation. Folder structure is important for the rules of the analysis to access the databases needed for the analysis, and to automatically detect the reference genome and mandatory databases for calling and annotation depending on the assembly defined in the manifest file (configured in the SampleSheet of each run), if any.

Folder structuer format: $FOLDER_DATABASES/<DATABASE_NAME>/<DATABASE_RELEASE>/<ASSEMBLY>/<DATABASE_FILE>.

  • Default: "$STARK_FOLDER_MAIN/databases"

Examples of folder structure:

  • $FOLDER_DATABASES/genomes/current/hg19/hg19.fa
  • $FOLDER_DATABASES/dbsnp/latest/hg19/dbsnp_138.hg19.vcf.gz
  • $FOLDER_DATABASES/dbnsfp/4.4a/hg19/dbNSFP4.4a.hg19.parquet

FOLDER_INPUT

All input data for the analysis, including raw data and metadata, should be stored in this folder. This folder will be used by the rules of the analysis to access the input data needed for the analysis. Folder structure is important for the rules of the analysis to access the input data needed for the analysis, and to automatically detect the input data needed for the analysis depending on the manifest file (configured in the SampleSheet of each run), if any.

  • Default: "$STARK_FOLDER_MAIN/input"

FOLDER_RUN

This folder will be used by the rules of the analysis to access the raw data of each run (from the sequencer, such as Illumina), organized as subfolder for each run (e.g. $FOLDER_RUN/<RUN_NAME>/), and to automatically detect the raw data information of each run on a SampleSheet file, or a analysis JSON file.

  • Default: "$FOLDER_INPUT/runs"

FOLDER_MANIFEST

This folder will be used by the rules of the analysis to access the manifest (Illumina format), design (BED format) and gene panels (BED format) files of each run (e.g. $FOLDER_MANIFEST/my_manifest.manifest, $FOLDER_MANIFEST/my_design.bed, $FOLDER_MANIFEST/my_gene_panel.genes). These files are automatically detected within the SampleSheet of the run, or the analysis JSON file of the run.

  • Default: "$FOLDER_INPUT/manifests"

FOLDER_PEDIGREE

This folder will be used by the rules of the analysis to access the pedigree file (PED format) of each run (e.g. $FOLDER_PEDIGREE/my_pedigree.ped). These files are automatically detected within the SampleSheet of the run, or the analysis JSON file of the run, by using GROUP and PROJECT defined by the application used for the run.

  • Default: "$FOLDER_INPUT/pedigree"

FOLDER_OUTPUT

This folder will be used to store all the results of the analysis, including intermediate files and final results. Subfolders for results, demultiplexing, log and tmp can be defined as absolute path, but we suggest to keep them as subfolders of the output folder for better organization and management of the data.

  • Default: "$STARK_FOLDER_MAIN/output"

FOLDER_DEMULTIPLEXING

This folder will be used by the rules of the analysis to store the results of the demultiplexing step (using SampleSheet file), including the demultiplexed FASTQ files and the demultiplexing report.

  • Default: "$FOLDER_OUTPUT/demultiplexing"

FOLDER_RESULTS

This folder will be used to store all the results of the analysis, including intermediate files and final results (files such as BAM, VCF, metrics, annotation files, and more).

  • Default: "$FOLDER_OUTPUT/results"

FOLDER_LOG

This folder will be used by the rules of the analysis to store log files of the analysis.

  • Default: "$FOLDER_OUTPUT/log" (Commented out by default)

FOLDER_TMP

This folder will be used by the rules of the analysis to store temporary files of the analysis, and to store temporary files of the tools used for the analysis (e.g. temporary files of GATK tools).

  • Default: "$FOLDER_OUTPUT/tmp" (Commented out by default)

FOLDER_REPOSITORY

This folder will be used by the rules of the analysis to copy some results of the analysis in a repository folder, organized by group and project (e.g. $FOLDER_REPOSITORY/<GROUP>/<PROJECT>/), and to automatically detect the files to copy in the repository folder depending on application. For a full run analysis, repository folder is automatically defined with group pand project structure. For other analyses, such as a single sample analysis, repository folder is empty, and no copy is performed. Leave it blank for no copy in repository folder.

  • Default: "$FOLDER_OUTPUT/repository" (for run analysis) or "" (for single sample analysis)

FOLDER_ARCHIVES

This folder will be used by the rules of the analysis to copy some results of the analysis in a archives folder, organized by group and project (e.g. $FOLDER_ARCHIVES/<GROUP>/<PROJECT>/), and to automatically detect the files to copy in the archives folder depending on application. For a full run analysis, archives folder is automatically defined with group pand project structure. For other analyses, such as a single sample analysis, archives folder is empty, and no copy is performed. Leave it blank for no copy in archives folder.

  • Default: "$FOLDER_OUTPUT/archives" (for run analysis) or "" (for single sample analysis)

FOLDER_FAVORITES

This folder will be used by the rules of the analysis to copy some results of the analysis in a favorites folder, organized by group and project (e.g. $FOLDER_FAVORITES/<GROUP>/<PROJECT>/), and to automatically detect the files to copy in the favorites folder depending on application. For a full run analysis, favorites folder is automatically defined with group pand project structure. For other analyses, such as a single sample analysis, favorites folder is empty, and no copy is performed. Leave it blank for no copy in favorites folder.

  • Default: ""

  • Configurations:

    • To NOT use favorites folder: FOLDER_FAVORITES=
    • To copy favorites within repository folder: FOLDER_FAVORITES=$FOLDER_REPOSITORY
    • To copy favorites within default favorites folder: FOLDER_FAVORITES=$FOLDER_OUTPUT/favorites
